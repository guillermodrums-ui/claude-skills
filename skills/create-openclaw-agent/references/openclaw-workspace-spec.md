# OpenClaw Workspace File Reference

Quick reference for what files an OpenClaw agent workspace expects. The skill generates these files; the
user installs them into their OpenClaw environment via INSTALL.md.

## The 8 workspace files

| File | Purpose | Size guideline |
|---|---|---|
| `SOUL.md` | Personality, voice, expressions, boundaries, knowledge | 100–300 lines |
| `AGENTS.md` | Operating rules, capabilities, handoff, memory instructions, channel rules | 80–200 lines |
| `IDENTITY.md` | Name, creature, vibe, emoji (4 fields) | ~5 lines |
| `USER.md` | User profile template (filled at runtime) | ~10 lines |
| `MEMORY.md` | Long-term curated memory (starts empty, filled over time) | ~10 lines |
| `HEARTBEAT.md` | Periodic check tasks — empty = no heartbeat calls | 1–10 lines |
| `TOOLS.md` | Channel formatting, env-specific config, external tool references | 20–80 lines |
| `openclaw.json` | Gateway config **snippet** (merged into user's real openclaw.json) | 15–40 lines |

Plus `INSTALL.md` (generated by the skill, in English, copy-paste install commands for the user).

## OpenClaw directory layout (for reference, not written by the skill)

When eventually installed, the workspace lives at `~/.openclaw/workspace-<slug>/` and the gateway config at
`~/.openclaw/openclaw.json`. The skill doesn't touch these — it only produces the files the user will copy
in.

## Key rules

- SOUL.md: personality + voice. Behavioral effects only, no life stories. Describe how the agent should feel.
- AGENTS.md: operational manual. Rules, memory, channel behavior, handoff protocol. If the agent has
  multiple intents with different rules (product info vs. dosing, etc.), use sub-sections under Capabilities.
- IDENTITY.md: 4 fields only. Optional avatar.
- USER.md: template at creation. Agent fills it as it learns about the user.
- MEMORY.md: empty at creation. Agent curates over time.
- HEARTBEAT.md: empty = no proactive API calls. Customer-facing bots usually don't need heartbeat.
- TOOLS.md: env-specific stuff. Channel formatting rules, RAG sources, external APIs the agent depends on.
- openclaw.json: JSON5 snippet (comments + trailing commas ok). Merge into user's config, don't replace.

## Channel config keys (openclaw.json fragment)

```json5
channels: {
  whatsapp: { enabled: true, dmPolicy: "open" | "pairing" | "allowlist" | "disabled" },
  telegram: { botToken: "<env>", dmPolicy: "pairing" },
  discord: { botToken: "<env>" },
  signal: { enabled: true },
  imessage: { enabled: true },
  web: { enabled: true }
}
```

## Known OpenClaw skills (to suggest in openclaw.json + INSTALL.md)

- `gog` — Google Calendar integration (OAuth). Trigger: scheduling, appointments.
- `web-search` — web search capability.
- `memory-search` — enhanced memory retrieval.
- `code-runner` — execute code snippets.

OpenClaw releases weekly — verify these exist with `/openclaw-scout` if the skill is uncertain.

## Model identifiers

Common values for `agent.model.primary`:

- `google/gemini-2.5-flash` — fast, cheap, good default for customer-facing bots
- `anthropic/claude-sonnet-4-6` — balanced
- `anthropic/claude-opus-4-6` — most capable
- `openai/gpt-4.1` — alternative

## WhatsApp formatting

- `dmPolicy: "open"` — anyone can message (typical for customer-facing bots)
- `dmPolicy: "pairing"` — requires QR code pairing (typical for personal assistants)
- No markdown tables — bullet lists
- Short messages (1–3 paragraphs)
- `**bold**` for emphasis, no headers
- Baileys plugin is free, QR-based

## External tools / data patterns

Typical integrations the skill should detect during the interview:

| Pattern | How to document |
|---|---|
| Google Calendar scheduling | Add `gog` skill to openclaw.json + `openclaw skill install gog` in INSTALL.md |
| Direct HTTP API called at runtime (agent fetches catalog/inventory live) | URL + endpoints + docs ref in TOOLS.md. Flag in INSTALL.md that wiring a custom skill/plugin is likely required. |
| Pre-synced data / RAG (catalog synced to a vector store ahead of time) | Source URL + sync pipeline + what's indexed in TOOLS.md. Refresh cadence in INSTALL.md. |
| Small static data (hours, address, menu) | Embed in SOUL.md Knowledge. No external tool needed. |

**Anti-hallucination rule** lives in AGENTS.md Red Lines. Phrase it around the actual source of truth
(e.g. "only confirm products that appear in the current API response / RAG context / SOUL.md Knowledge"),
not around a specific pattern name. This keeps the rule correct if the data-access pattern changes later.

## Handoff patterns

OpenClaw's **native** handoff is "silent mode": the agent stops replying and stays passive until
reactivated by another agent, the operator, a timeout, or a topic-change detector. That's the default
to assume when the end user doesn't describe their own mechanism.

Other patterns the skill should recognize **only when the end user explicitly describes them**:

| Mechanism | When to use |
|---|---|
| Silent mode (OpenClaw-native) | Default; most OpenClaw runtimes expect this |
| Tail-tag (e.g. `[HANDOFF]`) | Legacy/Python-integration pattern — only if the runtime parses the tag |
| Dedicated `handoff_to_human` skill | If a skill is configured for this |

Document whichever mechanism the user describes in AGENTS.md Handoff Protocol. Flag in INSTALL.md "Notes
& open items" that runtime wiring for reactivation (who/what resumes the agent) is an install-time
concern, regardless of mechanism.
